# HunyuanOCR 1.5 F16·Q4_K_M·Q5_K_M 실측 — 2026-10-21

## 결론

이 표본에서 Q5_K_M은 Q4_K_M보다 영어 누락을 줄였지만, 중국어 인식 정확도를
F16 수준으로 회복하지 못했다. 중국어 자동 탐지 영역에서는 Q4·Q5 모두 30/760자 오류,
F16은 8/760자 오류였다. 중국어 세로쓰기 두 영역의 읽기 순서가 차이 대부분을 설명한다.
Q5가 언제나 Q4보다 정확하다는 결론은 이 결과로 지지되지 않는다.

일본어는 기존 Hayai v2를 유지하는 판단이 여전히 타당하다. 이번 일본어 Q4의 오류 수가
F16·Q5보다 적은 것은 특정 후리가나 영역에서 본문만 출력한 영향이 크며, 전반적인
일본어 성능 역전으로 해석하면 안 된다. 기존 Hayai는 같은 일본어 표본에서
16px 여백 조건 2/384자, 여백 없는 조건 1/384자 오류였다.

앱 코드·모델 기본값·사용자 설정은 변경하지 않았다. 모델 통합이나 출시를 한 실험이 아니다.

## 데이터와 평가

- 중국어: 기존 4개 작품·20개 이미지에서 수동 영역 68개/776자와 자동 탐지 영역
  66개/760자. 두 영역 집합은 내용이 겹치므로 합쳐 독립 표본처럼 해석하지 않는다.
- 일본어: 기존 보관함 3개 작품·6페이지·32영역/384자. 원본을 읽기만 했다.
- 영어·스페인어: David Revoy 및 번역 기여자의 공개 만화 Pepper & Carrot
  1화 1–3페이지·3화 1–7페이지, 각 34영역, 각각 1,031자·1,124자.
  앞선 실험과 동일 URL에서 다시 받아 SHA-256 일치를 확인했다.
- 총 46개 원본 이미지에서 234영역. 기존 좌표와 전사를 고정하고 결과를 본 뒤 정답을
  수정하지 않았다. 모델 실행 전 작성한 assistant 전사이며 독립 검증된 human gold가 아니다.
- NFKC 후 문자·숫자만 남기고 Levenshtein 편집거리를 계산했다. 대소문자·악센트·작은
  가나를 유지하며 공백·문장부호는 제외한다. 완전일치는 이 정규화 기준이다.
- 모든 모델에 동일한 floor/ceil 좌표와 16px 흰 여백, 동일 프롬프트를 사용했다.
  전체 페이지 탐지·번역·식자 정확도를 평가한 점수가 아니다.
- 주요 점수는 별도의 편집거리 구현으로 재계산하여 원래 집계와 일치를 확인했다.
- 4개 기본 조건과 Q4·Q5 반복을 합쳐 총 1,404회 영역 인식을 완료했다.
  모두 정상 stop으로 종료했고 384토큰 상한 도달은 없었다.

## 정확도

셀: **문자 오류 수 / 정답 문자 수 (CER), 완전일치 영역 수 / 전체 영역 수**.
CER는 낮을수록 좋다.

| F16 + F16 vision     |  8/760 (1.05%), 61/66 | 16/776 (2.06%), 62/68 | 86/384 (22.40%), 17/32 | 0/1031 (0.00%), 34/34 | 2/1124 (0.18%), 32/34 |
| Q4_K_M + F16 vision  | 30/760 (3.95%), 59/66 | 16/776 (2.06%), 62/68 | 67/384 (17.45%), 17/32 | 7/1031 (0.68%), 33/34 | 2/1124 (0.18%), 32/34 |
| Q5_K_M + F16 vision  | 30/760 (3.95%), 59/66 | 17/776 (2.19%), 61/68 | 92/384 (23.96%), 16/32 | 0/1031 (0.00%), 34/34 | 3/1124 (0.27%), 31/34 |
| Q4_K_M + Q8_0 vision | 21/760 (2.76%), 59/66 | 16/776 (2.06%), 62/68 | 67/384 (17.45%), 17/32 | 7/1031 (0.68%), 33/34 | 2/1124 (0.18%), 32/34 |

F16 llama.cpp와 기존 Transformers BF16은 중국어 자동/수동·영어·스페인어 오류 수가
각각 8·16·0·2로 같았다. 일본어는 F16 86, 기존 BF16 87이었다.
따라서 양자화 비교의 직접 기준은 같은 llama.cpp의 F16이며, 이전 BF16 결과는
백엔드 차이가 얼마나 있는지 확인하는 보조 기준으로 썼다.

### 실제 차이가 난 영역

- `zh-AR028`: 오른쪽부터 읽어야 하는 세로 대사. F16은 원래 순서로 읽지만 Q4·Q5는
  왼쪽 열부터 출력해 각각 14자 편집 오류가 생겼다.
- `zh-AH017`: F16은 1자 누락, Q4·Q5는 열 순서가 바뀌면서 8자 오류.
  위 두 영역만으로 자동 영역에서 F16 대비 증가한 22오류 중 21오류를 설명한다.
- `en-ep03-7-02`: 정답 `It looks... ...Perfect`. Q4가 `It looks...`까지만 출력해
  `Perfect` 7자를 빠뜨렸다. F16·Q5는 모두 읽었다. 이전 Hayai 비교의 기울어진 포스터와
  다른 영역이다.
- `es-ep03-2-03`: Q5가 `prepárame`의 악센트를 빠뜨려 1오류가 추가됐다.
- `ja-2-2-04`: 본문만 정답으로 삼는 후리가나 영역. Q4는 본문만 출력해 0오류,
  F16은 후리가나를 섞어 22오류, Q5는 27오류였다. Q4의 일본어 합계가 낮은 주요 원인이다.
- 중국어 수동 영역은 Q4 16오류, Q5 17오류로 차이가 작았다. 양자화 영향은 영역 경계와
  읽기 순서에 따라 달라졌다. 정답을 보고 프롬프트나 후처리를 맞춘 결과는 포함하지 않았다.
- Q4 + Q8 vision의 중국어 자동 점수가 Q4 + F16 vision보다 좋은 현상도 관찰됐지만,
  이 작은 표본에서 이미지 모델 양자화가 일반적으로 유리하다고 해석하지 않는다.

## VRAM 실측

RTX 4090, Windows WDDM에서 해당 llama-server PID의 `GPU Process Memory`
`Dedicated Usage`를 약 100ms 간격으로 수집했다. Shared Usage는 시스템 공유 메모리이므로
전용 VRAM에 더하지 않았다. 동시에 NVML로 GPU 전체 사용량을 약 50ms 간격으로 기록했다.
다른 앱도 GPU를 쓰므로 전체 GPU 사용량을 OCR 단독 사용량으로 표시하지 않았다.
로드·준비·추론·종료 단계를 분리해 저장했다. 샘플링 사이의 짧은 피크는 놓칠 수 있다.

| 모델                 |   234개 영역 실행 최대 | 전체 페이지 단독 실행 최대 | 모든 시험에서 관측된 최대 |
| -------------------- | ---------------------: | -------------------------: | ------------------------: |
| F16 + F16 vision     | 2.926 GiB (2996.1 MiB) |     4.028 GiB (4124.2 MiB) |    4.028 GiB (4124.2 MiB) |
| Q4_K_M + F16 vision  | 2.236 GiB (2290.1 MiB) |     3.338 GiB (3418.2 MiB) |    3.344 GiB (3424.2 MiB) |
| Q5_K_M + F16 vision  | 2.279 GiB (2334.1 MiB) |     3.381 GiB (3462.2 MiB) |    3.387 GiB (3468.2 MiB) |
| Q4_K_M + Q8_0 vision | 1.990 GiB (2038.1 MiB) |     3.113 GiB (3188.2 MiB) |    3.113 GiB (3188.2 MiB) |

- 영역 정확도 시험: context 4,096, 한 번에 영역 1개.
- 전체 페이지 시험: context 10,240, 한 번에 페이지 1개, 언어별 가장 큰 원본 2장씩
  총 8장. 모든 모델에 같은 8장과 같은 설정을 사용했다. 입력을 별도 축소하지 않았고
  내부 이미지 전처리는 모델 런타임 기본 동작이다.
  중국어 2장은 각각 1748×2480, 일본어 2장은 1125×1600,
  영어·스페인어 4장은 1200×1660이었다.
- 공통: CUDA 전체 레이어 및 vision offload, Flash Attention on, logical batch /
  microbatch 512/512, 최대 출력 384 tokens. 페이지 시험은 VRAM 측정용이며 정답 점수는
  매기지 않았다. 긴 문서나 더 큰 context·batch·동시 요청의 최대 메모리를 보장하지 않는다.
- 표 마지막 열에는 연속 페이지 시험이 종료되기 전 관측치도 포함한다. 종료 원인은
  아래에 따로 기록했다. 완료된 8장 단독 실행만의 최대치는 가운데 열로 분리했다.
- Q5의 영역 실행 최대는 Q4보다 약 44MiB 높았다. Q4 텍스트 모델 파일이 작더라도
  별도 vision 모델·KV cache·연산 버퍼까지 필요하므로 파일 크기를 VRAM으로 보면 안 된다.
- 기존 PyTorch의 `max_memory_allocated/reserved`와 이번 WDDM 프로세스 전용 메모리는
  측정 범위가 다르므로 수치를 직접 나란히 놓고 양자화 절감률로 해석하지 않는다.

### 전체 페이지 연속 실행에서 발견한 런타임 종료

F16 + F16 vision, Q4 + F16 vision, Q5 + F16 vision 모두 같은 순서의 4번째 페이지
처리 중 서버가 종료됐다. 첫 3페이지는 각각 완료했고, Windows 종료 코드는
`3221225477 (0xC0000005, access violation)`이었다. 로그에 CUDA OOM은 없었다.
이를 정상 완료나 메모리 부족으로 보고하지 않는다.

Q5로 해당 4번째 페이지를 새 서버에서 단독 실행하면 정상 완료됐다.
이어 네 설정 모두 8개 페이지를 매번 새 서버에서 실행해 전부 완료했다.
이는 연속 실행 상태에 연관된 런타임 문제라는 추정을 뒷받침하지만, 네이티브 크래시의
정확한 코드 원인을 특정하거나 수정한 것은 아니다. 실제 앱 통합 전 해결해야 할 제한이다.
234개 작은 영역의 연속 인식에서는 이 종료가 발생하지 않았다.

## 재현 조건과 무결성

- GGUF: `prithivMLmods/HunyuanOCR-1.5-GGUF-Updated`
  revision `9ddd3b47beb0de305ecd89a717748bac080d7aee`.
- llama.cpp 공식 Windows CUDA 12.4 배포 `b11103`, commit
  `828fdf282e195300c2965bd9511807e24ed53bdb`. DFlash는 사용하지 않았다.
- 비교 기준 원본: `Tencent/HunyuanOCR@47644ecc4fc854efa4f505155158831f36773ee4`.
  F16 GGUF의 텍스트 모델 tensor 266개를 기존 BF16 safetensors를 해당 dtype으로
  변환한 값과 직접 비교해 **266/266 완전 일치**를 확인했다. vision tensor 전체에 대한
  같은 방식의 비교까지 수행한 것은 아니다.
- 다운로드한 모델은 고정 revision의 LFS byte size·SHA-256, runtime ZIP은 공식
  release digest와 대조했다. Q5 파일은 399,793,280 bytes,
  SHA-256 `1c42656f106f14e178b499c4c4b67735a9a5039a5c3bdbabb0832f61c3bff0c6`.
- 프롬프트: `提取图片中的所有文字，按照阅读顺序输出原文，不要翻译，不要解释。`
- temperature 0, top_k 1, top_p 1, min_p 0, seed 123, repetition penalty 1.08,
  repeat_last_n = context 길이, prompt cache off, parallel 1, CPU threads 4.
- 처음 두 준비 실행은 API의 `repeat_last_n=-1` 검증에서 HTTP 400으로 실패했다.
  유효한 context 길이로 바꾼 뒤 시작한 실행만 정확도 집계에 포함했다.
- 합친 정답 파일 SHA-256:
  `345a746fe252473c29c8bfc80f06cb893c4844627e520509a0cce4bade901359`.
- Q4_K_M + F16 vision 재실행: 234영역 중 원문 출력 234/234 일치.
- Q5_K_M + F16 vision 재실행: 234영역 중 원문 출력 234/234 일치.
